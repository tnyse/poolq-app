# General Rules Description

## Purpose
The General Rules document serves as the comprehensive coding standards and best practices guide for the PoolQ application. It ensures consistency, maintainability, and quality across the entire codebase by providing clear guidelines for development practices.

## Structure
The General Rules are organized into the following key sections:

1. **General Coding Principles**
   - Minimalistic approach
   - Code duplication prevention
   - Change management
   - Code organization
   - Documentation standards
   - Error handling
   - Script management
   - Function design
   - Naming conventions

2. **Frontend Specific Rules (Flutter/Dart)**
   - Material Design implementation
   - Widget organization
   - Project structure
   - File size limits
   - State management
   - Provider implementation
   - Firebase integration
   - Stream management
   - Navigation patterns

3. **Backend Specific Rules (Node.js)**
   - Input validation
   - Error handling
   - Authentication
   - Authorization

4. **Technical Stack & Environment**
   - Development tools
   - Framework versions
   - Environment setup
   - Platform-specific guidelines

5. **Code Review & Impact Assessment**
   - Change evaluation
   - Testing requirements
   - Review process
   - Risk assessment

## Auto-Attachments
The following files are automatically attached to the General Rules for reference:

1. **Development Timeline**
   - File: `.cursor/rules/DEVELOPMENT_TIMELINE.md`
   - Purpose: Provides context for implementation timing
   - Updated: Weekly

2. **PRD**
   - File: `.cursor/rules/PRD.mdc`
   - Purpose: Links rules to feature requirements
   - Updated: With PRD changes

3. **Style Guide**
   - File: `lib/constants/style_guide.md`
   - Purpose: Defines code style and formatting
   - Updated: With style changes

4. **Architecture Documentation**
   - File: `docs/architecture.md`
   - Purpose: Explains system design and patterns
   - Updated: With architectural changes

## Usage Guidelines

### For Developers
1. Follow all coding standards in daily development
2. Reference rules before implementing new features
3. Use auto-attached documents for specific guidelines
4. Report any rule conflicts or ambiguities

### For Code Reviewers
1. Use rules as the basis for code reviews
2. Ensure compliance with all standards
3. Provide constructive feedback
4. Document any rule violations

### For Team Leads
1. Enforce rule compliance
2. Update rules based on team feedback
3. Monitor rule effectiveness
4. Train new team members

## Version Control
- Rules are version controlled in the `.cursor/rules` directory
- Changes require team review and approval
- All updates must be documented
- Previous versions are archived

## Maintenance
- Regular reviews every month
- Updates based on team feedback
- Version control for all changes
- Automated attachment updates
